# 수동 재전송 API를 운영자 Bearer 토큰으로 보호하는 이유

- 상태: 승인
- 결정일: 2026-09-13

## 배경

수동 재전송은 `FAILED`·`DEAD_LETTER` 전달을 다시 실행합니다. 외부 호출과 전달 이력을 바꾸는 운영 기능이므로 일반 이벤트 발행자에게 열어둘 수 없습니다.

현재 프로젝트에는 사용자 계정이나 조직별 권한 모델이 없습니다. 이 단계에서 JWT 발급 서버나 외부 인증 제공자를 추가하면 재전송 권한보다 인증 인프라가 구현의 중심이 됩니다. 한편 경로를 로컬 loopback에만 노출하는 방식은 배포 환경의 접근 제어 계약이 되지 못합니다.

## 결정

`POST /api/v1/deliveries/{deliveryId}/redeliveries`에 Spring Security의 요청 단위 권한 검사를 적용합니다.

- 클라이언트는 `Authorization: Bearer <token>`을 보냅니다.
- 애플리케이션은 `HOOK_RELAY_OPERATOR_TOKEN` 환경변수에서 32자 이상의 운영자 토큰을 읽습니다.
- 토큰이 일치하면 `OPERATOR` 권한을 부여합니다.
- 토큰 누락, 형식 오류, 불일치는 세부 원인을 구분하지 않고 `401 Unauthorized`로 응답합니다.
- 인증 상태는 HTTP 세션에 저장하지 않습니다.
- 토큰은 원문끼리 비교하지 않고 SHA-256 digest를 만든 뒤 상수 시간 비교를 사용합니다.
- 이벤트 접수, 구독 등록, Actuator 경로의 기존 접근 정책은 바꾸지 않습니다.

운영자 토큰이 없거나 32자보다 짧으면 애플리케이션 시작을 중단합니다. 설정 실수로 보호 경로가 공개되는 상황보다 명시적인 기동 실패를 선택했습니다.

## 결과

재전송 경로의 인증과 권한은 Controller 밖의 보안 필터 체인에서 먼저 검사됩니다. 인증에 실패한 요청은 전달 상태를 조회하거나 바꾸지 않습니다. 오류 응답은 다른 API와 같은 `code`, `message`, `path`, `traceId` 구조를 사용합니다.

고정 토큰 하나만 사용하므로 운영자별 식별, 개별 권한 회수, 무중단 토큰 교체는 지원하지 않습니다. 여러 운영 주체가 필요해지면 현재 `OPERATOR` 권한 규칙은 유지하고 인증 부분을 OIDC 또는 사내 인증 체계로 교체합니다. 배포 환경에서는 TLS를 적용하고 Compose에 포함된 로컬 시연용 토큰을 재사용하지 않습니다.

## 검토한 대안

### 별도 API Key 헤더

구현은 간단하지만 표준 `Authorization` 헤더와 Spring Security 인증 흐름을 활용하기 어렵습니다. HTTP 클라이언트와 프록시가 공통으로 다루는 Bearer 형식을 선택했습니다.

### JWT 또는 외부 OIDC

운영자별 신원과 토큰 만료를 다룰 수 있습니다. 현재는 사용자·조직 모델과 인증 제공자가 없어 검증할 대상보다 구성이 커집니다. 운영 주체가 늘어나는 시점에 도입 여부를 다시 판단합니다.

### 네트워크 접근 제한만 사용

방어 계층으로는 유효하지만 애플리케이션 자체의 권한 계약이 없습니다. loopback 바인딩은 로컬 시연 보호로 유지하고 API 인증을 별도로 적용합니다.
