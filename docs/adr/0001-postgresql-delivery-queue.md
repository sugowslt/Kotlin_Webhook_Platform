# ADR 0001: PostgreSQL 작업 큐부터 시작합니다

- 상태: 채택
- 작성일: 2026-09-11

## 배경

HookRelay는 이벤트를 받은 뒤 외부 Webhook 서버로 전달합니다. 외부 서버의 timeout이나 `5xx`가 Event API 응답까지 지연시키지 않으려면 접수와 전달을 분리해야 합니다. 처리 중 프로세스가 종료돼도 미완료 작업을 다시 찾을 수 있어야 합니다.

## 선택

첫 구현은 PostgreSQL에 이벤트와 전달 작업을 같은 트랜잭션으로 저장합니다. Worker는 `FOR UPDATE SKIP LOCKED`로 실행할 작업을 선점하고, lease가 만료된 작업은 다른 Worker가 다시 가져갑니다.

Kafka를 먼저 연결하지 않습니다. 현재 단계에서는 이벤트 접수, 작업 저장, 재시도와 복구가 하나의 저장소 안에서 어떻게 동작하는지 검증하는 편이 범위를 통제하기 쉽습니다.

## 대안

### Kafka

처리량 확장과 소비자 분리에 유리합니다. 다만 DB 저장과 Kafka 발행 사이의 원자성, broker 운영과 장애 복구까지 첫 단계의 검증 범위에 들어옵니다. PostgreSQL 작업 큐에서 실제 병목이 확인된 뒤 검토합니다.

### 인메모리 큐

구현은 간단하지만 프로세스 재시작 시 대기 작업을 잃습니다. 장애 복구를 확인해야 하는 프로젝트 목적과 맞지 않아 제외했습니다.

### Redis

지연 작업과 빠른 조회에 사용할 수 있지만, 첫 구현부터 PostgreSQL과 Redis의 상태를 함께 맞춰야 합니다. 작업 큐의 기준 저장소가 필요한 현재 단계에서는 사용하지 않습니다.

## 검증 상태

- [x] 여러 Worker가 같은 작업을 동시에 선점하지 않는지 확인했습니다.
- [x] 선점 직후 프로세스가 종료됐을 때 lease 만료 후 복구되는지 확인했습니다.
- [x] 대기 작업 100건에서 적체 상태와 선점 시간을 측정했습니다.
- [x] 전달 작업 500건을 3회 처리해 단일 Worker의 로컬 기준값을 기록했습니다.
- [x] 대기열 500건·1,000건과 Worker 1개·2개·4개 조합을 각각 3회 측정했습니다.
- [x] 측정 결과를 기준으로 Kafka 또는 Redis 도입 여부를 다시 판단했습니다.

Worker 4개의 평균 처리량은 Worker 1개보다 500건에서 3.46배, 1,000건에서 3.73배 높았습니다. 선점 쿼리 평균은 Worker 4개에서 약 19~21ms였고 선점 실패와 중복 처리는 없었습니다. 이 범위에서는 PostgreSQL이 확장을 막는 병목이라고 판단할 근거가 부족하므로 Kafka와 Redis 도입을 미룹니다.

실제 환경에서 작업 대기 시간이 목표를 넘고 선점 쿼리나 DB 부하가 원인으로 확인될 때 broker 도입을 다시 검토합니다. 외부 네트워크, TLS, 수신 지연, 재시도와 더 큰 대기열은 이번 판단 범위에 포함하지 않았습니다. 상세 결과는 [다중 Worker 확장 측정](../worker-scaling.md)에 기록했습니다.
