# 다중 Worker 확장 측정

## 측정 목적

PostgreSQL 작업 큐를 공유하는 Worker 수를 늘렸을 때 처리량이 어떻게 변하는지 확인했습니다. 대기열 크기는 500건과 1,000건, Worker 수는 1개·2개·4개로 바꿨습니다. 각 조합은 유효한 결과가 3개 모일 때까지 반복했습니다.

이벤트 접수 시간과 컨테이너 시작 시간은 처리량에서 제외했습니다. 모든 작업이 `PENDING`이고 시도 이력이 0건인 상태에서 Worker를 시작한 뒤, 첫 시도 `started_at`부터 마지막 시도 `finished_at`까지를 처리 구간으로 계산했습니다.

## 실행 조건

| 항목 | 조건 |
| --- | --- |
| 측정 일시 | 2026-09-15 |
| 호스트 | Windows 11 10.0 amd64 |
| 애플리케이션 | Java 17.0.18, Gradle 9.3.1, Spring Boot 4.0.3 |
| Docker | Engine 29.7.2, Compose 5.5.1 |
| 데이터베이스 | PostgreSQL 17.11, 기존 volume 유지 |
| 적재 | `grafana/k6:2.1.0`, `shared-iterations`, VU 50개 |
| 대기열 | 매회 고유 이벤트 500건 또는 1,000건 |
| Worker | 1개·2개·4개, 인스턴스당 batch 20건, fixed delay 1초, lease 30초 |
| 수신기 | 로컬 Python 수신기, 응답 지연 0ms, `204 No Content` |
| 반복 | 각 조합에서 유효한 결과 3회 |

API 애플리케이션의 Worker는 `hook-relay.worker.enabled=false`로 끄고, Compose의 `worker-scale` profile만 확장했습니다. 확장 Worker는 호스트 포트를 열지 않고 같은 PostgreSQL과 수신기를 사용합니다. 실행이 끝나면 확장 Worker를 제거하고 API 애플리케이션 Worker와 수신기 지연을 기본값으로 되돌립니다.

## 결과 해석

Worker를 1개에서 2개로 늘리자 두 대기열에서 처리량이 약 2배가 됐습니다. 4개에서는 500건 기준 3.46배, 1,000건 기준 3.73배였습니다. Worker 4개의 선점 쿼리 평균은 약 19~21ms로 늘었지만 선점 실패나 중복 처리는 없었습니다.

따라서 현재 로컬 조건과 Worker 4개 범위에서는 PostgreSQL이 확장을 막는 병목이라고 판단할 근거가 없습니다. 반대로 운영 한계를 입증한 것도 아닙니다. 외부 네트워크와 TLS, 수신 지연, 재시도, 더 큰 DB와 대기열은 포함하지 않았습니다. Kafka나 Redis는 실제 환경에서 작업 대기 시간이 목표를 넘거나 선점 쿼리와 DB 부하가 확장 한계로 확인될 때 다시 검토합니다.

## 제외한 회차와 보완

1,000건·Worker 4개 세 번째 실행에서 첫 시도 한 건이 `HTTP/1.1 header parser received no bytes`로 끝나 `RETRY_SCHEDULED`가 됐습니다. 나머지 999건은 성공했고 해당 건도 기본 Worker 복구 후 두 번째 시도에서 `204`로 성공했습니다.

성공 응답만 비교하는 이번 측정 기준과 달리 시도 횟수가 2회가 됐으므로 해당 회차는 처리량 표본에서 제외했습니다. 같은 조건을 다시 실행해 이벤트·전달·성공 시도·수신 요청이 각각 1,000건이고 비성공 시도가 0건인 결과를 세 번째 표본으로 사용했습니다. 전체 확장 측정 이력에서 같은 비성공 오류는 이 1건뿐이어서 반복되는 장애로 단정하지 않았습니다.

처음 Worker 2개로 500건을 처리했을 때 DB에는 성공 500건이 기록됐지만 수신기 로그는 492줄만 집계됐습니다. Python `ThreadingHTTPServer`의 여러 요청 스레드가 표준 출력에 동시에 기록하며 줄 경계가 합쳐진 것이 원인이었습니다. 로그 출력 구간을 하나의 lock으로 보호한 뒤 같은 조건에서 DB와 수신 로그가 모두 500건으로 일치했고, 이후 유효 회차에도 같은 방식을 적용했습니다.

Worker 활성 조건 테스트를 처음 추가했을 때 테스트용 설정을 일반 `@Configuration`으로 선언해 PostgreSQL 통합 테스트의 `clock` bean과 충돌했습니다. 테스트 전용 설정임을 명시하는 `@TestConfiguration`으로 바꿨고, 전체 58개 테스트를 다시 실행해 실패 0개를 확인했습니다.

## 재현 방법

Docker Desktop을 실행한 뒤 저장소 루트에서 실행합니다.

```powershell
.\demo\run-worker-scaling-demo.ps1
```

대기열 크기, Worker 수, 적재 VU, 반복 횟수는 인자로 바꿀 수 있습니다. 처리량 배율을 계산하므로 Worker 수에는 1이 포함돼야 합니다.

```powershell
.\demo\run-worker-scaling-demo.ps1 `
    -EventCounts @(500, 1000) `
    -WorkerCounts @(1, 2, 4) `
    -SeedVus 50 `
    -Repetitions 3
```

스크립트는 실행 전 활성 전달 작업이 없는지 확인하고 기존 데이터는 삭제하지 않습니다. 실패하면 확장 Worker와 수신기의 마지막 100줄을 먼저 출력한 뒤 임시 Worker를 제거하고 기본 설정을 복구합니다.
